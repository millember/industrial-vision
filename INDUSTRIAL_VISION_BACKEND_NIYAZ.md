# Industrial Vision — серверная часть Нияза

Практический план разработки FastAPI и БД. Связанный документ: [общий план команды](INDUSTRIAL_VISION_PLAN.md).

Дата: 9 ноября 2026 года. Это план и предлагаемый контракт для согласования с Константином и Софией. Кроме health endpoint перечисленные API пока не реализованы.

## 1. Твоя зона ответственности

**Нияз: сервер, база данных и интеграция готовой модели.**

Ты реализуешь:

- ID цехов, сотрудников, оборудования и типов поломок.
- Вход сотрудников, профиль, роли и доступ по цеху.
- Каталог оборудования, паспортные данные, сроки службы.
- Общую базу знаний: виды дефектов, описание, примеры, рекомендации.
- Приём и закрытое хранение фотографий с камеры и из галереи.
- Вызов модели Софии и проверку её ответа.
- Преобразование наблюдений в предварительную оценку состояния.
- Сохранение осмотров, сообщений, проверок специалиста и аудита.
- Внутренние уведомления; при наличии времени — серверную часть FCM.
- Docker, конфигурацию, API-документацию и серверные проверки.

Константин делает Android, камеру, AR, интерфейс, кеш и получение пушей. София делает модель, распознавание и координаты. Алина тестирует и готовит презентацию. Нияз не берёт на себя обучение модели и реализацию ARCore.

## 2. Исходная точка и результат

В репозитории уже есть `backend/app/main.py`, зависимости FastAPI/Uvicorn, Dockerfile и Compose. Работает `GET /api/v1/health`. БД и бизнес-маршрутов пока нет.

Минимальный результат твоей работы:

```text
Авторизованный сотрудник
  → выбирает оборудование своего цеха
  → отправляет фото
  → сервер вызывает модель
  → сохраняет осмотр и предварительную оценку
  → отдаёт JSON с рамкой и рекомендацией
  → сотрудник нажимает «Сообщить»
  → сервер сохраняет сообщение и аудит
  → ответственный видит внутреннее уведомление
```

Данные переживают перезапуск. Ошибка модели не превращается в успешную диагностику. Повтор запроса с тем же ключом не создаёт второй осмотр или сообщение.

## 3. Подход к реализации

Использовать существующий FastAPI-проект. Планируемый стек хранения — SQLite, SQLAlchemy и Alembic; их добавление является будущей задачей, сейчас они не установлены в рамках этого документа.

Разделять HTTP, сценарии приложения и внешние зависимости по мере появления логики:

```text
backend/app/
├── main.py
├── api/                 # маршруты, входные/выходные Pydantic-схемы
├── dependencies.py      # сборка зависимостей и текущий пользователь
├── application/         # создание осмотра, сообщения, проверка, порты
├── domain/              # статусы, правила оценки, ошибки
└── infrastructure/      # БД, модели ORM, файлы, модель Софии, FCM
```

HTTP-слой разбирает запрос и проверяет доступ. Сценарий приложения управляет операцией и транзакцией. Адаптер модели изолирует внешний формат. Домен не импортирует FastAPI или ORM. Для простого чтения каталога не создавать цепочку пустых сервисов.

Предложенная структура — направление развития, не задача немедленно переписать каркас.

| `idempotency_keys` | Состояние повторяемого запроса, пользователь, маршрут, хеш содержимого, сохранённый результат |

### Ограничения данных

- Сервер назначает ID. Уникальны логин, инвентарный номер, коды цехов и дефектов.
- Включить внешние ключи SQLite, проверить индексы по оборудованию/дате и получателю уведомления.
- Не хранить пароли открытым текстом. Секреты и токены не коммитить.
- Время хранить в UTC; локальное отображение выполняет Android.
- Осмотр хранит автора и цех на момент события. В аудите сохранять необходимые снимки значений для истории при переименовании сущностей.
- Состояние конкретного оборудования выводить из последней подтверждённой оценки; отдельно отдавать последний предварительный осмотр. До подтверждения состояние оборудования может быть `UNKNOWN`.
- Срок службы из паспорта не является результатом модели и сам по себе не доказывает поломку.
- Отсутствующий дефект при `OK`/`UNKNOWN` хранить как `null`, а не создавать фиктивную поломку.
- Для MVP один осмотр содержит одну фотографию и одну итоговую оценку. Несколько фото можно добавить позже без изменения смысла истории.

## 5. Доступ и роли

Предлагаемая матрица для согласования командой:

| Действие в разрешённом цехе | Рабочий | Слесарь | Мастер | Инженер | Начальник цеха |
|---|---|---|---|---|---|
| Смотреть оборудование | Да | Да | Да | Да | Да |
| Создать осмотр и сообщение | Да | Да | Да | Да | Да |
| Смотреть свою историю | Да | Да | Да | Да | Да |
| Смотреть сообщения цеха | Свои | Назначенные | Да | Да | Да |
| Подтвердить/отклонить оценку | Нет | Нет | Нет | Да | Нет |
| Закрыть проблему после проверки | Нет | Нет | Да | Да | Нет |

Регистрацию и редактирование справочников для MVP можно оставить серверной seed-команде. Публичной самостоятельной выдачи роли или цеха нет. Изменение ролей — отдельный защищённый административный сценарий.

Сервер берёт автора из токена, а цех — из доступного оборудования; не доверяет присланным `author_id`, `role` и `workshop_id`. Для каждого ID проверяется доступ к соответствующему объекту, включая фото, историю, сообщение и уведомление.

Вход выдаёт ограниченный по времени токен доступа. Android передаёт `Authorization: Bearer <access_token>`. После истечения токена в MVP возможен повторный вход; refresh-поток не нужен до явной потребности.

## 6. API для Константина

Все маршруты ниже относительны к `/api/v1`. Только health уже существует.

| Метод и путь | Назначение |
|---|---|
| `GET /health` | Работоспособность API |
| `POST /auth/login` | JSON с `login` и `password`; ответ с `access_token`, `token_type`, `expires_in` |
| `GET /me` | ID, имя, роль, цех текущего пользователя |
| `GET /workshops` | Только доступные цеха |
| `GET /equipment` | Доступное оборудование; фильтр `workshop_id`, пагинация |
| `GET /equipment/{id}` | Карточка, паспорт, последняя предварительная и подтверждённая оценки |
| `GET /defect-types` | Каталог дефектов; фильтр по типу оборудования |
| `POST /inspections` | Фото на анализ, `multipart/form-data` |
| `GET /inspections/{id}` | Результат сохранённого осмотра |
| `GET /equipment/{id}/inspections` | История доступного оборудования |
| `GET /photos/{id}` | Защищённая выдача изображения |
| `POST /inspections/{id}/reports` | Сообщение о проблеме из диалога Android |
| `POST /inspections/{id}/reviews` | Проверка инженером |
| `POST /issues/{id}/close` | Закрытие проблемы с причиной после проверки |
| `GET /notifications` | Уведомления текущего пользователя |
| `PATCH /notifications/{id}` | Пометка своего уведомления прочитанным: `{"is_read": true}` |
| `POST /devices` | Привязка FCM-токена к текущему пользователю, если реализованы пуши |

Для списков использовать `limit` по умолчанию 20, максимум 100, `offset` по умолчанию 0; ответ `items`, `total`, `limit`, `offset`. Историю сортировать по `created_at DESC, id DESC`.

### Сканирование

`POST /inspections` принимает:

| Поле | Тип | Правило |
|---|---|---|
| `equipment_id` | integer | Выбранное оборудование разрешённого цеха |
| `source` | string | `CAMERA` или `GALLERY` |
| `image` | file | JPEG/PNG, первоначально до 10 МиБ и до 20 млн пикселей после декодирования |

Заголовок `Idempotency-Key` обязателен для создания осмотра и сообщения. Android генерирует новый UUID для нового действия и повторно использует его при сетевом повторе.

Первый MVP: синхронный анализ с ограниченным временем ожидания. Успешный ответ — `201 Created`, формат результата приведён в [общем плане](INDUSTRIAL_VISION_PLAN.md#6-контракт-между-android-и-сервером). Если модель объективно слишком медленная, отдельно согласовать `202 Accepted` и опрос состояния; не менять поведение незаметно для Android.

В MVP оборудование выбирается до снимка: ID физического агрегата не выводится из распознанного класса «саморез». Автоматическую идентификацию экземпляра через QR/маркер можно добавить отдельно с Константином.

### Кнопка «Сообщить»

`POST /inspections/501/reports`

```json
{
  "comment": "Прошу проверить крепление на макете."
}
```

Комментарий необязательный, максимум 2000 символов. Оборудование, состояние, цех и автор для формы берутся из осмотра и текущего пользователя. Повторно передавать их как доверенные значения не требуется.

Пример ответа `201 Created`:

```json
{
  "report_id": 91,
  "inspection_id": 501,
  "issue_id": 18,
  "author_id": 7,
  "workshop_id": 1,
  "created_at": "2026-11-13T11:32:00Z",
  "notification_status": "QUEUED"
}
```

`QUEUED` означает постановку внутренних уведомлений в обработку, а не подтверждённую доставку пуша на телефон. Отмена диалога не отправляет запрос. Для MVP сообщение о дефекте допускается для завершённого осмотра `WARNING`/`CRITICAL`; для `OK`/`UNKNOWN` возвращать `409 REPORT_NOT_APPLICABLE`. Общий ручной запрос проверки без распознанного дефекта — отдельное будущее расширение.

### Проверка специалистом

`POST /inspections/501/reviews`

```json
{
  "decision": "CONFIRMED",
  "status": "WARNING",
  "comment": "Неполное прилегание подтверждено."
}
```

`decision`: `CONFIRMED` или `REJECTED`. При подтверждении инженер задаёт обоснованный итоговый статус; при отклонении итоговый статус — `UNKNOWN`, пока не выполнен новый осмотр. Не превращать отклонение дефекта автоматически в доказанную норму.

Проверка создаёт новую запись, исходный ответ модели сохраняется. `review_status` результата вычисляется по последней проверке. Для подтверждения использовать `Idempotency-Key` и проверку версии последней оценки, чтобы параллельные решения не перезаписывали друг друга молча.

### Ошибки

Предлагаемый единый формат новых бизнес-ошибок:

```json
{
  "error": {
    "code": "MODEL_UNAVAILABLE",
    "message": "Анализ временно недоступен. Попробуйте позже."
  }
}
```

| HTTP | Случай |
|---|---|
| `401` | Нет действительного токена |
| `403` | Роль не разрешает операцию |
| `404` | Объект не найден или не доступен пользователю по цеху |
| `409` | Ключ повтора использован с другим содержимым, конфликт версии или недопустимое действие |
| `413` | Слишком большой файл |
| `415` | Неподдерживаемый фактический формат изображения |
| `422` | Некорректные поля или повреждённое изображение |
| `502` | Некорректный ответ внешней модели |
| `503` | Модель недоступна |
| `504` | Истекло время ожидания модели |

Формат ошибок валидации FastAPI также привести к согласованному контракту. Сбой сервиса модели — HTTP-ошибка; корректный ответ модели «недостаточно данных» — сохранённая оценка `UNKNOWN`. Это разные ситуации.

## 7. Интеграция с Софией

Получить от Софии до подключения:

1. Способ запуска: Python-вызов в процессе или отдельный HTTP-сервис.
2. Поддерживаемые классы: норма, недокручен, отсутствует, выкручен; не считать их все готовыми заранее.
3. Формат confidence, согласованный порог и ограничения качества снимка.
4. Формат координат и все преобразования: resize, padding, поворот.
5. Версию модели, контрольные фото, примеры плохих снимков и неизвестных объектов.
6. Измеренные требования к ресурсам и время анализа; Нияз проверяет их на целевом сервере.

Внутренний результат адаптера содержит `class_code`, `confidence`, `box`, размеры снимка и `model_version`. Методы и поля окончательно согласовать с реальным выходом модели. Не требовать от модели ID пользователя, цеха или оборудования.

Нияз проверяет известность класса, конечность чисел, диапазон confidence `[0, 1]`, положительные размеры рамки и её попадание в изображение. `box` в API — целые пиксели `[x, y, width, height]` на снимке после EXIF-нормализации. Координаты модели с resize/letterbox преобразуются обратно до выдачи Android.

Недопустимую рамку не отдавать для отрисовки. Если локализация обязательна для этого класса, результат считать некорректным; если класс допускает оценку без рамки, вернуть `box: null` с объяснением. Отсутствие крепежа допустимо только при известной зоне установки.

Заглушка разрешена только в явно включённом демонстрационном режиме: `analysis_source: "MOCK"`. Реальная модель: `"MODEL"`. Нельзя автоматически переключаться на заглушку при ошибке настоящей модели.

## 8. Правила оценки

| Поддерживаемый результат | Итог | Рекомендация |
|---|---|---|
| Полностью установленный крепёж | `OK/GREEN` | Проверяемых отклонений не обнаружено |
| Недокручен | `WARNING/ORANGE` | Проверить крепление; для безопасного макета — докрутить |
| Отсутствует/выкручен в известном месте | `CRITICAL/RED` | Передать специалисту; проверить и восстановить крепление |
| Низкая уверенность, плохая видимость, неизвестный класс | `UNKNOWN/GRAY` | Повторить снимок или запросить ручную проверку |

Красный статус до проверки остаётся предварительным, `review_status: UNREVIEWED`. Не брать температуру из обычной фотографии. Не подставлять паспорт другого экземпляра только по совпадению типа оборудования.

Для исходного JSON Константина сохранить поля `object`, `status`, `color`, `defect`, `box`, `recommendation`; дополнительно согласовать ID, размеры, confidence и признаки источника/проверки. Любое изменение контракта заранее передавать Константину.

## 9. Фото, транзакции и повторы

- Декодировать файл и проверять фактический тип; ограничивать байты и размер распакованного изображения.
- Имя хранения генерирует сервер. Путь клиента не используется. Фото выдаются через защищённый endpoint.
- Нормализовать поворот до анализа, сохранять именно соответствующее координатам изображение; не публиковать лишние EXIF-данные.
- Не держать транзакцию SQLite открытой во время вызова модели.
- Короткой транзакцией резервировать ключ повтора и осмотр `PROCESSING`, затем вызвать модель вне транзакции и короткой транзакцией записать результат.
- После ошибки отмечать осмотр `FAILED` с причиной; сохранять понятный ответ для повторов. Для новой попытки анализа клиент создаёт новое действие с новым ключом.
- Одновременный запрос с тем же ключом во время обработки получает `409 REQUEST_IN_PROGRESS`; после завершения — сохранённый ответ.
- Уникальное ограничение для ключа включает пользователя и операцию; хеш запроса защищает от повторного использования ключа для другого фото или комментария.
- При сбое между файлом и БД удалять осиротевший файл либо отмечать его для очистки. Не удалять файлы активных осмотров.
- Незавершённые после аварийного перезапуска `PROCESSING` переводить в явное ошибочное состояние по согласованному таймауту; не оставлять вечное ожидание.

## 10. Сообщения, аудит и уведомления

Сканирование само по себе не отправляет пуш. При «Сообщить» сервер в одной транзакции сохраняет сообщение, запись аудита, связь с открытой проблемой и внутренние уведомления.

Группировка MVP: открытая проблема по паре `(equipment_id, defect_type_id)`. Это допустимо для одного проверяемого крепления на макете. Если одинаковых креплений несколько, добавить `component_id` или ID места установки; иначе разные неисправности сольются.

Первое сообщение создаёт событие уведомления. Следующие сообщения об этой открытой проблеме добавляют наблюдения без повторного пуша. Изменение подтверждённого статуса может создать отдельное событие. Закрытие проблемы допускает новое событие при повторном возникновении. Уникальные ограничения БД защищают создание открытой проблемы и уведомлений от гонок.

Получатель должен иметь разрешённый цех, нужную роль и назначение на тип оборудования. До отдельных назначений мастер и инженер своего цеха могут получать все типы — это правило фиксируется явно. Пуш не раскрывает фотографию или чувствительный комментарий на экране блокировки; подробности доступны после входа.

Аудит содержит автора, серверное время, оборудование, цех, исходную оценку и действия проверки. Записи не редактируются через обычный API. Аудит обеспечивает прослеживаемость действий, но не является неоспоримым доказательством причины поломки.

FCM — следующий слой: регистрация устройств, сервисные секреты, отправка из сохранённой очереди, повторные попытки и удаление недействительных токенов. Ошибка FCM не откатывает сообщение. Доставка может повториться, поэтому Android группирует её по ID события. При отсутствии FCM внутренние уведомления остаются рабочими.

## 11. Порядок твоей разработки в 10 шагах

Все пункты ниже — будущие задачи; не отмечать их выполненными по одному наличию этого документа.

| Шаг | Что сделать Ниязу | Наблюдаемый результат |
|---|---|---|
| 1 | Согласовать API с Константином и выход модели с Софией | Команда принимает примеры запросов, ответов, ошибок и координат |
| 2 | Подключить SQLite, миграции и демоданные | Цех, сотрудники, макет, паспорт и дефекты читаются после перезапуска |
| 3 | Реализовать вход, профиль и проверки доступа | Пользователь получает токен; чужой цех недоступен |
| 4 | Выдать оборудование и базу знаний | Android получает карточку и рекомендации по ID |
| 5 | Принимать фото и вызывать явный mock-адаптер | Работают multipart, валидация, `MOCK`-маркер и обработка ошибок |
| 6 | Подключить реальную модель | Те же API работают с `MODEL`, без изменения клиента |
| 7 | Сохранять осмотры и выдавать историю | Фото, оценка и модельная версия доступны по ID и в истории |
| 8 | Реализовать «Сообщить», аудит и внутренние уведомления | Сообщение появляется у нужного сотрудника один раз |
| 9 | Добавить проверку инженером; FCM — по времени | Исходное наблюдение сохраняется; итог проверки виден отдельно |
| 10 | Проверить API и запуск на сервере | Команда проходит сценарий на APK, данные переживают перезапуск |

Приоритет первого дня — пройти путь фото → реальная модель → JSON на Android. Разработку API с mock-адаптером вести параллельно с подготовкой модели, явно показывая временный характер заглушки.

## 12. Серверные критерии готовности

| Проверка | Ожидаемый результат |
|---|---|
| Вход с неверным паролем | Нет токена, понятная ошибка |
| Пользователь другого цеха запрашивает фото/осмотр | Нет доступа к содержимому |
| Валидное фото | Осмотр сохранён, ответ соответствует схеме |
| Изображение с EXIF-поворотом | Размеры и координаты совпадают с выданным фото |
| Пустой, повреждённый или слишком большой файл | Предусмотренная ошибка, без успешного осмотра |
| Плохой снимок или неизвестное оборудование | `UNKNOWN`, без выдуманной нормы/паспорта |
| Модель недоступна или превысила таймаут | `503/504`, без фиктивного результата |
| Модель вернула координаты вне снимка | Ошибка или допустимый `box: null` по правилам класса |
| Один ключ повтора отправлен дважды, в том числе параллельно | Один осмотр/сообщение; явный ответ на текущую обработку |
| Тот же ключ и другое содержимое | `409` |
| Два сообщения об одной открытой проблеме | История сохраняется, уведомление не дублируется |
| Инженер подтверждает/отклоняет оценку | Есть отдельная запись проверки, исходная оценка сохранена |
| Роль без права проверки отправляет review | `403` |
| Перезапуск контейнера | БД и фотографии сохранены |
| Ошибка доставки FCM, если включён | Сообщение доступно, отправка может быть повторена |

При реализации проверить политики отдельно, API — на успешных и запрещённых сценариях, транзакции и ограничения — на реальной SQLite, повторы — конкурентными запросами. Это план будущих проверок; сейчас они не запускались и не считаются пройденными.

## 13. Развёртывание и передача команде

Текущий запуск описан в [README](README.md). В ходе реализации добавить постоянные volumes для SQLite и фото, миграции и отдельную команду демоданных. Текущий Compose запускает Uvicorn с `--reload`; для демонстрационного размещения подготовить конфигурацию без autoreload и проверить один процесс записи SQLite.

Конфигурация: путь БД и фото, секрет авторизации, режим модели, её адрес или путь весов, таймаут анализа; FCM-секреты только при включённой доставке. Для внешнего доступа настроить HTTPS. На телефон передаётся доступный ему адрес сервера: `localhost` на телефоне обозначает сам телефон.

До размещения модели на домашнем сервере измерить фактическое потребление ресурсов. Разрешение использовать домашний сервер и данные согласовать отдельно; этот план не выполняет развёртывание и не меняет инфраструктуру.

Передать Константину базовый URL, Swagger, демо-ID, тестовые учётные записи и примеры ошибок. Софии — принятый формат адаптера и результаты проверки на сервере. Алине — сценарии проверки, статусы реально готовых функций и ограничения для презентации.

## 14. Что пока не брать в обязательный объём

- Обучение модели и сбор датасета вместо Софии.
- Android, ARCore и локальную БД телефона вместо Константина.
- Автоматическую диагностику любых агрегатов и температур по RGB-фото.
- Полную офлайн-синхронизацию, сложную админку и расширенные отчёты.
- Несколько моделей и поддержку множества дефектов до первого сквозного результата.

Твоя первая цель: сервер принимает настоящее фото, получает проверяемый результат модели, сохраняет его и отдаёт Android согласованный JSON; затем надёжно обрабатывает «Сообщить» с автором, временем, цехом и адресным уведомлением.
