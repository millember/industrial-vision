# Industrial Vision — общий план команды

Хакатон «Кибер 102», кейс №3: интеллектуальная система анализа состояния промышленного оборудования.

Дата плана: 9 ноября 2026 года. Основание — обсуждение команды и присланные макеты. Полное ТЗ заказчика ещё нужно сверить: этот документ не заменяет его.

## 1. Цель и границы проекта

Сотрудник фотографирует оборудование через Android-приложение. Сервер передаёт снимок модели компьютерного зрения, получает наблюдения, сохраняет осмотр и возвращает состояние, проблемную область и рекомендацию. Пользователь может сообщить о проблеме; ответственные сотрудники своего цеха видят сообщение и историю.

Демонстрационный объект — саморез, винт или болт в известном месте крепления на макете узла оборудования. Он позволяет показать норму, неполное закручивание и отсутствие крепежа. Компрессор на иллюстрации — концепция интерфейса, а не обещание распознавания компрессоров готовой моделью.

Нияз реализует только серверную часть и БД. Обучение модели, Android и AR выполняют другие участники.

## 2. Команда и ответственность

| Участник | Основная зона | Что передаёт команде |
|---|---|---|
| Константин | Android на Java, камера, галерея, интерфейс, ARCore, локальный кеш, клиент уведомлений | APK, отправку фото, отображение ответа API, форму «Сообщить» |
| София | Компьютерное зрение и анализ визуальных признаков | Модель или API, классы, координаты, confidence, ограничения и тестовые изображения |
| Нияз | FastAPI, SQLite, хранение фото, авторизация, правила доступа, интеграция модели, история, уведомления | Рабочий API, серверную БД, адаптер модели, документацию и запуск Docker |
| Алина | Тестирование и презентация | Сценарии проверок, список ошибок, демонстрационный сценарий и презентацию |

Нияз и София согласуют формат результата модели. Нияз и Константин согласуют HTTP-контракт до независимой разработки клиентов и сервера.

## 3. Архитектура и источник данных

```text
Android: камера / галерея / AR / кеш
                  |
             HTTPS API
                  |
               FastAPI
                  |
       Сценарии приложения и правила
          /          |          \
       SQLite    Хранилище фото   Адаптер модели → модель Софии
          |
   История, сообщения, аудит, уведомления → FCM → Android
```

| Компонент | Решение |
|---|---|
| Android | Java + Android SDK; ARCore для поддерживаемых устройств |
| Backend | Python + FastAPI |
| БД | SQLite для демонстрации; единая серверная база |
| Модель | Подбирает София; YOLO — возможный вариант, пока не обязательный выбор |
| Фото | Закрытое файловое хранилище сервера, метаданные в БД |
| Запуск | Docker Compose |
| Уведомления | Сначала внутренний список; FCM при готовности Android и настройки проекта |

Сервер — источник истины для сотрудников, цехов, оборудования, дефектов и осмотров. Телефон хранит кеш разрешённых данных с серверными ID. Прямого доступа Android к SQLite нет. Полная двусторонняя офлайн-синхронизация — отдельная задача после основного сценария.

В репозитории сейчас есть FastAPI, Docker Compose и `GET /api/v1/health`. БД, авторизация, анализ снимков и уведомления этим планом ещё только предусматриваются.

## 4. Состояния и отображение

| Наблюдение для демо | status | color | Подпись |
|---|---|---|---|
| Крепёж полностью установлен | `OK` | `GREEN` | Саморез: Норма |
| Крепёж установлен не до конца | `WARNING` | `ORANGE` | Саморез: Недокручен |
| Крепёж отсутствует в известной точке | `CRITICAL` | `RED` | Саморез: Отсутствует |
| Крепёж выкручен из известного места | `CRITICAL` | `RED` | Саморез: Выкручен |
| Снимок плохой, объект неизвестен или данных мало | `UNKNOWN` | `GRAY` | Не удалось определить |

Три цвета показывают определённое состояние. Серый — служебный результат, предотвращающий ложную зелёную оценку при отсутствии данных.

`CRITICAL` до проверки специалистом означает предварительно критическую оценку. Поле `review_status` отдельно показывает `UNREVIEWED`, `CONFIRMED` или `REJECTED`. Подтверждённую неисправность нельзя приписывать любому красному ответу модели.

Нельзя заключать, что саморез отсутствует, только потому что детектор ничего не нашёл. Нужны известная точка установки, видимая область и поддержка такого сценария моделью. Обычная RGB-камера не измеряет температуру: для температурной оценки нужны данные датчика или тепловизора.

## 5. План в 10 этапов

### Этап 1. Согласовать демонстрационный сценарий и контракты

**Участники:** вся команда; API фиксирует Нияз.

- Сверить обязательные требования с полным ТЗ заказчика.
- Выбрать макет оборудования и конкретное место крепления.
- Зафиксировать классы модели и состояния, которые она действительно различает.
- Согласовать загрузку фото, JSON, ошибки, координаты и кнопку «Сообщить».
- Согласовать разрешения ролей и критерии подтверждения результата.

**Готово, когда:** Android может работать с согласованным примером JSON, София знает формат выхода, Алина имеет проверяемый сценарий.

### Этап 2. Создать единую БД и демонстрационные данные

**Ответственный:** Нияз.

Цеха, сотрудники, оборудование, паспорт, типы дефектов и рекомендации получают серверные ID. Осмотры, фото и сообщения связываются с этими ID. Каталог дефектов и примеров образует общую базу знаний.

**Готово, когда:** после перезапуска сервера данные сохраняются; у оборудования и сотрудника есть привязка к цеху.

### Этап 3. Реализовать API и доступ

**Ответственный:** Нияз; интеграция Android — Константин.

Вход, профиль, списки доступного оборудования, карточки, создание осмотра, получение результата и истории. Сервер проверяет пользователя и цех при каждом доступе к объекту и фото.

**Готово, когда:** Android получает реальные данные, а пользователь другого цеха не читает чужие осмотры по ID.

### Этап 4. Подключить Android-клиент

**Ответственный:** Константин.

Камера, отправка фотографии, индикатор ожидания, отображение результата, ошибок и текущего пользователя. Кнопка «Сообщить» открывает форму с оборудованием, состоянием, цехом, автором и необязательным комментарием.

Существующую заглушку сканирования заменить обращением к серверу. До подключения модели демонстрационные ответы должны быть явно помечены как заглушка.

**Готово, когда:** приложение показывает ответ настоящего API и не выдаёт сетевую ошибку за успешный анализ.

### Этап 5. Получить рабочий результат компьютерного зрения

**Ответственный:** София; серверный адаптер — Нияз.

София готовит модель, примеры, классы, уверенность и координаты; объясняет ограничения отсутствующего и выкрученного крепежа. Нияз передаёт фото, проверяет ответ, ограничивает ожидание и преобразует результат к API.

**Готово, когда:** поддерживаемый дефект определяется на заранее отложенных примерах; неизвестный объект не получает выдуманную оценку.

### Этап 6. Выдавать состояние и рекомендацию

**Ответственный:** Нияз; правила наблюдений согласуются с Софией.

Сервер сопоставляет класс с каталогом дефектов и предварительным статусом. Рекомендация берётся из согласованной базы знаний. Низкая уверенность и неполные данные дают `UNKNOWN`, а не норму. Для реального оборудования рекомендации должны учитывать регламент; текст «докрутить» относится к безопасному демонстрационному макету.

**Готово, когда:** одинаковое наблюдение даёт одинаковую оценку, неизвестные классы не проходят как известные.

### Этап 7. Отобразить области и AR

**Ответственный:** Константин; координаты — София и Нияз.

Сервер возвращает прямоугольник на проанализированном снимке. Android учитывает поворот, масштаб, обрезку и зеркальность изображения. Для настоящей привязки к сцене Константин реализует ARCore и проверяет поведение при движении телефона.

Двумерная рамка поверх фото сама по себе не является устойчивой AR-привязкой. Для ответа на старый кадр нельзя без отслеживания переносить рамку на новый кадр живой камеры.

**Готово, когда:** рамка совпадает с областью исходного снимка; если по ТЗ требуется AR, привязка отдельно демонстрируется на устройстве.

### Этап 8. Сохранять историю и сообщения

**Ответственный:** Нияз; экраны — Константин; проверки — Алина.

Сканирование сохраняет осмотр. Нажатие «Сообщить» отдельно создаёт сообщение по этому осмотру. Сохраняются серверное время, автор, цех, оборудование, наблюдение и комментарий. Уполномоченный специалист подтверждает или отклоняет оценку с отдельной записью истории.

**Готово, когда:** сообщение видно после перезапуска; повторная отправка из-за плохой сети не создаёт копию.

### Этап 9. Добавить адресные уведомления

**Ответственный:** Нияз; FCM-клиент и разрешения — Константин.

- Роли: рабочий, слесарь, мастер, инженер, начальник цеха.
- Получатели определяются по цеху, роли и назначению на тип оборудования.
- Автоматический анализ сохраняется в истории; уведомление создаётся при отправке сообщения либо подтверждении специалистом.
- Повторное сообщение об открытой проблеме группируется; сетевой повтор не создаёт новый пуш.
- Источник и время фиксируются на сервере, текст не объявляет неподтверждённую поломку фактом.

Пример: «Иванов И.И. сообщил о возможном отсутствии крепежа: макет компрессора, Цех 1, 14:32. Нужна проверка».

**Готово, когда:** нужный сотрудник видит уведомление, другой цех его не получает; повтор доставки обрабатывается без дублей. Тест пушей выполняется на совместимой сборке APK.

### Этап 10. Проверить интеграцию и подготовить защиту

**Участники:** вся команда; тестирование и презентация — Алина.

Проверить норму, недокрученный и отсутствующий крепёж, плохой снимок, неизвестный объект, недоступность модели, потерю сети, историю, права и повторы запросов.

**Готово, когда:** есть APK, инструкция запуска сервера, Swagger, демоданные, проверенная модель и воспроизводимый сценарий защиты. Реальные результаты и заглушки различимы.

## 6. Контракт между Android и сервером

Планируемые маршруты имеют префикс `/api/v1`. Подробности, ошибки и серверная последовательность приведены в [плане Нияза](INDUSTRIAL_VISION_BACKEND_NIYAZ.md).

| Действие | API |
|---|---|
| Вход и профиль | `POST /auth/login`, `GET /me` |
| Доступные цеха и оборудование | `GET /workshops`, `GET /equipment`, `GET /equipment/{id}` |
| Каталог дефектов | `GET /defect-types` |
| Фото с камеры или из галереи | `POST /inspections` — multipart |
| Сохранённый результат | `GET /inspections/{id}` |
| История оборудования | `GET /equipment/{id}/inspections` |
| Кнопка «Сообщить» | `POST /inspections/{id}/reports` |
| Проверка специалистом | `POST /inspections/{id}/reviews` |
| Внутренние уведомления | `GET /notifications`, `PATCH /notifications/{id}` |
| Регистрация устройства, при FCM | `POST /devices` |

Пример ответа сканирования; значения иллюстративные, это не текущий ответ работающего сервера:

```json
{
  "inspection_id": 501,
  "equipment_id": 125,
  "object": "Саморез",
  "status": "WARNING",
  "color": "ORANGE",
  "defect_id": 2,
  "defect_code": "FASTENER_PROTRUSION",
  "defect": "Недокручен",
  "box": [120, 340, 80, 80],
  "image": {"width": 720, "height": 1280},
  "confidence": 0.91,
  "recommendation": "На демонстрационном макете докрутить саморез до упора.",
  "review_status": "UNREVIEWED",
  "analysis_source": "MODEL",
  "model_version": "fastener-demo-v1"
}
```

`box` — `[x, y, width, height]` в пикселях изображения после нормализации EXIF-поворота. Начало координат — левый верхний угол. Модельный адаптер возвращает координаты к этому изображению, даже если модель работала с уменьшенной копией. Размеры и фото должны соответствовать друг другу.

Для `UNKNOWN` цвет `GRAY`, а `defect_id`, `defect_code`, `box` и `confidence` могут быть `null`. Для нормы `box` может обозначать найденный объект, но не выдуманный дефект. Один осмотр в MVP описывает одно выбранное оборудование и одну итоговую оценку; расширение до нескольких областей требует согласования контракта.

## 7. Приоритеты

| Приоритет | Объём |
|---|---|
| P0 | Согласовать ТЗ; реальное распознавание поддерживаемых состояний; камера и API; координаты; паспорт и рекомендации; требуемая по ТЗ AR-функция; сохранение результата и кнопка «Сообщить» |
| P1 | Галерея, история, проверка специалистом, внутренние уведомления, расширение ролевых прав |
| P2 | FCM, полноценная офлайн-синхронизация, много типов оборудования, отчёты |

Базовые авторизация и проверка цеха входят в серверную основу, даже если расширенная ролевая модель отложена. Неподтверждённость результата обозначается с первого рабочего ответа.

## 9. Что команда должна передать друг другу

- Константин → Ниязу: пример multipart-запроса, формат авторизации в клиенте, поведение камеры и форма сообщения; позже — FCM-токен.

- Алина → команде: результаты проверок, последовательность защиты и список известных ограничений.

## 10. Честная демонстрация

Телефон не определяет произвольные поломки без поддерживающей модели. Паспорт поступает из БД конкретного оборудования, а не придумывается по фотографии. Аудит показывает, кто и когда отправил сообщение; сам по себе он не доказывает техническую причину дефекта или виновность сотрудника.

Если модель или AR не готовы, это фиксируется как незавершённая часть. Красивая рамка и тестовый JSON не заменяют распознавание и требуемую AR-функцию.
