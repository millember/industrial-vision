# Android ↔ сервер — контракт 1.0-draft

Статус: контракт частично реализован. На шаге 7 backend работают вход через `POST /api/v1/auth/token`, профиль, справочники, карточка оборудования, mock-анализ, сохранение фото/осмотров и история. Шаг 6 отложен: настоящая модель не подключена. Сообщения, проверки специалистов и уведомления остаются планом. Текущие ограничения описаны ниже и в [README](../README.md#сохранение-и-история--шаг-7).
Все пути ниже включают `/api/v1`. JSON — UTF-8; серверное время — ISO 8601 UTC с `Z`. Авторизация: `Authorization: Bearer <access_token>`.

## Основные операции

| Метод | Путь | Успех | Вход и результат |
|---|---|---|---|
| GET | /api/v1/health | 200 | Существующий ответ `{"status":"ok"}` |
| POST | /api/v1/auth/token | 200 | JSON `login/password` → `access_token/token_type/expires_in/user`; токен на 24 часа с продлением при активности |
| GET | /api/v1/me | 200 | `id/full_name/role/workshop_id` |
| GET | /api/v1/workshops | 200 | Только доступные цеха |
| GET | /api/v1/equipment | 200 | Оборудование разрешённого цеха; фильтр `workshop_id` пока не реализован |
| GET | /api/v1/equipment/{equipment_id} | 200 | Карточка и паспорт; оценки осмотров появятся на следующих шагах |
| GET | /api/v1/defect-types | 200 | Общий каталог с рекомендациями; фильтр `equipment_type_id` пока не реализован |
| POST | /api/v1/inspections/preview | 200 | Реализовано: multipart-фото → предварительный ответ `MOCK`, без сохранения |
| POST | /api/v1/inspections | 201 | multipart-фото → сохранённый результат |
| GET | /api/v1/inspections/{id} | 200 | Сохранённый результат, доступный этому пользователю |
| GET | /api/v1/equipment/{id}/inspections | 200 | История доступного оборудования |
| GET | /api/v1/photos/{id} | 200 | Бинарное нормализованное изображение; проверка доступа |
| POST | /api/v1/inspections/{id}/reports | 201 | JSON `comment` → отдельное сообщение |
| POST | /api/v1/inspections/{id}/reviews | 201 | Решение уполномоченного инженера |
| POST | /api/v1/issues/{id}/close | 200 | JSON `reason`; мастер/инженер после проверки |
| GET | /api/v1/notifications | 200 | Только уведомления текущего пользователя |
| PATCH | /api/v1/notifications/{id} | 200 | JSON `{"is_read":true}`, только своё уведомление |
| POST | /api/v1/devices | 201 | При FCM: JSON `token/platform`; владелец из авторизации |

Первая реализация API должна вводить эти операции по шагам; этот документ не требует создать их все на шаге 1. Подробные схемы дополнительных CRUD/read-операций уточняются перед соответствующим шагом. Зафиксированная сейчас граница интеграции — снимок, результат, сообщение и формат ошибок.

Планируемая пагинация: `limit=20` (1–100), `offset=0` (неотрицательный), ответ `items`, `total`, `limit`, `offset`. На шаге 4 списки справочников возвращаются обычными JSON-массивами до 500 записей. Для будущей истории предусмотрена сортировка по `created_at DESC, id DESC`.

## Карточка оборудования — реализовано на шаге 4

`GET /api/v1/equipment/{equipment_id}` возвращает:

```json
{
  "id": 125,
  "name": "Макет узла",
  "inventory_number": "DEMO-125",
  "workshop_id": 1,
  "type_id": 1,
  "passport": "Демонстрационный макет, крепление М6."
}
```

ID иллюстративные. `passport` — сохранённый текст, может быть пустой строкой. Авторизация обязательна: сотруднику доступен только свой цех, администратору — все. Для чужого и несуществующего ID одинаковый ответ `404` с `{"detail":"Оборудование не найдено"}`. Неавторизованный запрос получает `401`.

`GET /api/v1/defect-types` возвращает массив объектов `id/name/status/recommendation`, сохранённых администратором. Это общая база знаний без привязки к типу оборудования и без автоматической оценки состояния конкретного объекта. Текущие ошибки чтения используют поле `detail`; единый формат ошибок, описанный ниже для будущих операций, ещё не внедрён.

## Загрузка снимка

На шаге 5 реализован только `POST /api/v1/inspections/preview` с полями из таблицы ниже и ответом `200`, без сохранения. Он явно включается настройкой `ANALYSIS_MODE=mock`; по умолчанию `disabled` даёт `503 MODEL_UNAVAILABLE`. Mock всегда возвращает `UNKNOWN/GRAY`, `analysis_source=MOCK`, `model_version=null`, `box=null`, `confidence=null`, `defect_id=null`, `defect_code=null`, `review_status=UNREVIEWED`, а также `equipment_id`, `object`, `source`, `created_at`, `image`, `defect`, `recommendation` и `reason`. Размеры соответствуют снимку после EXIF-поворота. Метаданные не передаются адаптеру. Ответ не содержит `inspection_id` и `photo_id`.

Preview принимает один кадр JPEG/PNG, ограничивает всё multipart-тело 10 МиБ + 64 КиБ и проверяет лимит файла отдельно. Проверка формата опирается на байты, не имя или MIME. Повреждённые файлы и неверные поля отклоняются. Авторизация и CSRF для cookie проверяются до чтения тела. Ошибки preview используют формат `error.code/message` из раздела ниже. Проверка цеха выполняется до декодирования изображения. `Idempotency-Key` для preview не нужен: он не создаёт записей.

На шаге 7 реализован `POST /api/v1/inspections` с сохранением, `201` и ключами повторов. В отсутствие модели используется только явно включённый `MOCK`; автоматического перехода к mock при сбое нет.

`POST /api/v1/inspections`, `Content-Type: multipart/form-data`.
Клиентская HTTP-библиотека сама задаёт boundary.

| Поле | Формат | Ограничение |
|---|---|---|
| equipment_id | integer | Положительный ID доступного оборудования |
| source | string | CAMERA или GALLERY |
| image | file | JPEG/PNG, до 10 МиБ (10 485 760 байт) и 20 000 000 декодированных пикселей |

Сервер проверяет фактический формат, а не только расширение/MIME клиента. Автор берётся из токена, цех — из выбранного оборудования. В MVP нет массива снимков и автоматической идентификации экземпляра по фотографии.

Заголовок `Idempotency-Key` — UUID нового действия. Сетевой повтор сохраняет этот UUID и те же поля/байты снимка.

## Сохранённые осмотры и фото — реализовано на шаге 7

Ответ `201` содержит поля результата из таблицы ниже, а также `author_id`, `workshop_id`, `source` и `reason`. В текущем mock-режиме оценка всегда `UNKNOWN/GRAY`, `analysis_source=MOCK`, `model_version=null`. `GET /api/v1/inspections/{id}` возвращает тот же JSON с `200`. У одного осмотра одно фото, поэтому `photo_id` равен `inspection_id`.

`GET /api/v1/photos/{photo_id}` выдаёт сохранённое нормализованное изображение с проверкой цеха и SHA-256. Оно соответствует размерам результата, не содержит исходных EXIF-данных и не публикуется статически. При отсутствии файла или нарушении целостности — `503 STORAGE_UNAVAILABLE`.

`GET /api/v1/equipment/{id}/inspections` принимает `limit=20` (1–100), `offset=0` (от 0). Возвращает `items`, `total`, `limit`, `offset`; порядок `created_at DESC, id DESC`. Элемент истории: `inspection_id/equipment_id/author_id/workshop_id/source/created_at/processing_status/result/error`. `result` — полный сохранённый результат или null, `error` — объект `error.code/message` или null.

В истории видны `PROCESSING`, `COMPLETED` и `FAILED`. Чтение незавершённого результата даёт `409 REQUEST_IN_PROGRESS`; чтение неуспешного — сохранённый HTTP-статус и ошибку. Обработка старше пяти минут при запуске или обращении становится `FAILED` с `503 ANALYSIS_INTERRUPTED`; новая попытка требует нового ключа. Транзакции БД охватывают только резервирование и фиксацию результата, не анализ или файловый ввод-вывод.

Права на осмотр и фото проверяются по сохранённому цеху и текущему цеху оборудования; администратор видит все цеха. Чужой и несуществующий ID дают одинаковый `404`. Хранилище выбирает сервер через `PHOTO_STORAGE=local|nextcloud`, без влияния клиента; выбранный backend сохраняется с осмотром. По умолчанию используется локальный постоянный volume. Настройки и ограничения переключения приведены в README.

## Результат осмотра

Форма `201` при создании и `200` при чтении одинакова. Примеры содержат вымышленные ID.

| Поле | Тип | Значение |
|---|---|---|
| inspection_id | integer | ID сохранённого осмотра |
| equipment_id | integer | ID выбранного оборудования |
| photo_id | integer | Защищённое фото через /api/v1/photos/{id} |
| created_at | string | Время создания на сервере, UTC |
| object | string | Отображаемое имя проверяемого объекта |
| status | string | OK, WARNING, CRITICAL, UNKNOWN |
| color | string | GREEN, ORANGE, RED, GRAY; однозначно соответствует status |
| defect_id | integer/null | ID каталога, null для OK/UNKNOWN |
| defect_code | string/null | Стабильный код каталога, null для OK/UNKNOWN |
| defect | string | Подпись: Норма, Недокручен, Отсутствует, Выкручен, Не удалось определить |
| box | array/null | [x, y, width, height] в целых пикселях нормализованного фото |
| image | object | Положительные integer width/height нормализованного фото |
| confidence | number/null | [0, 1]; оценка модели, не вероятность исправности агрегата |
| recommendation | string | Согласованный текст базы знаний |
| review_status | string | UNREVIEWED, CONFIRMED, REJECTED |
| analysis_source | string | MODEL или явно включённый MOCK |
| model_version | string/null | Версия артефакта модели; null у MOCK |

Примеры для клиента:

- [Норма](examples/inspection-ok.json)
- [Недокручен](examples/inspection-warning.json)
- [Отсутствует](examples/inspection-critical.json)
- [Недостаточно данных](examples/inspection-unknown.json)

Поля исходного предложения Константина сохранены: `object/status/color/defect/box/recommendation`. Добавлены ID, размеры, время и сведения об источнике/проверке. `photo_id` позволяет получить именно тот снимок, которому соответствует рамка.

Пример неизвестного результата относится к корректно выполненному анализу с недостаточными данными. Недоступность модели — HTTP-ошибка и не выдаётся как такой результат.

## Координаты

Ноль — левый верхний угол. X направлен вправо, Y вниз. Ограничения: `x >= 0`, `y >= 0`, `width > 0`, `height > 0`, `x + width <= image.width`, `y + height <= image.height`.

Сначала сервер нормализует EXIF-поворот, затем анализирует и сохраняет фото в этой ориентации. Адаптер отменяет resize/padding модели. Android масштабирует координаты под фактическое отображение, учитывает crop/letterbox и зеркальность.

Для нормы рамка может показывать объект. Для UNKNOWN рамка в MVP равна null. Для отсутствующего крепежа рамка относится к известной зоне установки. Нельзя переносить область старого снимка на новый кадр камеры без отслеживания. API не возвращает 3D-координаты.

## Кнопка «Сообщить»

`POST /api/v1/inspections/501/reports`. Обязательны авторизация и `Idempotency-Key`.

Запрос: [report-request.json](examples/report-request.json). Допускается пустой объект `{}`: комментарий необязателен, string, до 2000 символов.

Ответ: [report-response.json](examples/report-response.json).

- Сообщение создаётся только для доступного завершённого WARNING/CRITICAL-осмотра.
- Для OK/UNKNOWN возвращается `409 REPORT_NOT_APPLICABLE`.
- Автор — текущий пользователь; цех и оборудование определяет сервер по осмотру.
- Отмена Android-диалога не вызывает API.
- `notification_status: QUEUED` означает постановку уведомления в обработку, не доставку FCM.
- Повторное наблюдение может ссылаться на ту же открытую issue и сохраняется без повторного пуша.

## Проверка специалистом

`POST /api/v1/inspections/{id}/reviews`. Только инженер доступного цеха. Обязательны `Idempotency-Key` и JSON:

```json
{
  "decision": "CONFIRMED",
  "status": "WARNING",
  "comment": "Неполное прилегание подтверждено.",
  "expected_review_id": null
}
```

`expected_review_id` обязателен: null при отсутствии проверки, иначе ID последней проверки, известной клиенту. При изменившейся версии — `409 REVIEW_CONFLICT`. Успех возвращает `review_id/inspection_id/decision/status/comment/author_id/created_at`. Следующий запрос использует полученный `review_id`.

CONFIRMED допускает OK/WARNING/CRITICAL, подтверждение должно быть обосновано специалистом. REJECTED требует UNKNOWN. Новая запись не удаляет исходную оценку модели. Отклонённая оценка отображается как UNKNOWN/GRAY; исходное наблюдение остаётся в истории.

## Повторы и ошибки

Ключ повтора ограничен пользователем и операцией (включая целевой ID). Одинаковое содержимое после завершения возвращает сохранённые тело и HTTP-статус, без повторного создания сущности. При другом содержимом — `409 IDEMPOTENCY_CONFLICT`. Хеш multipart учитывает значения полей и байты изображения, не случайный boundary.

Пока первый запрос выполняется: `409 REQUEST_IN_PROGRESS`. Клиент может повторить запрос с тем же ключом после ожидания. После сохранённой ошибки новая попытка анализа — новое действие с новым UUID.

Единый формат ошибки: [error-model-unavailable.json](examples/error-model-unavailable.json). Новые ошибки валидации FastAPI также должны соответствовать этому формату; существующий health не меняется.

| HTTP | code | Смысл |
|---|---|---|
| 401 | UNAUTHENTICATED | Нет действительного токена |
| 403 | FORBIDDEN | Роль запрещает действие |
| 404 | NOT_FOUND | Нет объекта или он за пределами разрешённого цеха |
| 409 | REQUEST_IN_PROGRESS / IDEMPOTENCY_CONFLICT | Конфликт повторяемого запроса |
| 409 | REPORT_NOT_APPLICABLE / REVIEW_CONFLICT | Недопустимое действие или устаревшее решение |
| 413 | IMAGE_TOO_LARGE | Превышены байты либо декодированные пиксели |
| 415 | UNSUPPORTED_IMAGE_TYPE | Фактический формат не JPEG/PNG |
| 422 | VALIDATION_ERROR / INVALID_IMAGE | Неверные поля или повреждённый файл |
| 502 | MODEL_INVALID_RESPONSE | Некорректный ответ модели |
| 503 | MODEL_UNAVAILABLE | Модель недоступна |
| 503 | STORAGE_UNAVAILABLE | Хранилище недоступно, файл отсутствует или повреждён |
| 503 | ANALYSIS_INTERRUPTED | Прерванная обработка осмотра |
| 504 | MODEL_TIMEOUT | Истекло время анализа |

Авторизация проверяется до чтения ресурса. Детали исключений, пути файлов, токены и секреты в ошибку не попадают.
