# Требования Industrial Vision — шаг 1

Версия контракта: `1.0-draft`. Дата: 9 ноября 2026 года.
Основание: [общий план](../INDUSTRIAL_VISION_PLAN.md) и [план сервера](../INDUSTRIAL_VISION_BACKEND_NIYAZ.md).
Статус: предложение Нияза для интеграции. Подтверждение Константина и Софии ещё не получено.

## Ответственность

| Участник | Результат |
|---|---|
| Нияз | FastAPI, БД, авторизация, файлы, адаптер модели, история, сообщения и серверные уведомления |
| Константин | Android/Java, камера, галерея, рамки, ARCore, кеш и FCM-клиент |
| София | Модель, классы, признаки дефектов, координаты, качество и ограничения |
| Алина | Проверки, сценарий демонстрации, презентация |

Нияз не обучает модель и не реализует Android/AR. Реализация сервера не зависит от завершения Android: на этапе интеграции используются согласованные запросы и примеры. Временный mock модели всегда обозначается явно.

## Минимальный сквозной сценарий

1. Сотрудник входит и получает оборудование своего цеха.
2. Выбирает макет агрегата с одним известным местом крепления.
3. Android отправляет снимок и ID выбранного оборудования.
4. Сервер вызывает модель Софии и сохраняет результат.
5. Android показывает предварительный статус, рекомендацию и область на снимке.
6. Пользователь нажимает «Сообщить» и отправляет необязательный комментарий.
7. Сервер сохраняет автора, время, оборудование, сообщение и внутреннее уведомление.
8. Уполномоченный инженер позже подтверждает или отклоняет оценку.

Класс «саморез» не идентифицирует физический экземпляр агрегата. Его ID выбирается до снимка. Для отсутствующего крепежа нужна известная и видимая точка установки. По одному отсутствию детекции нельзя устанавливать дефект.

## Проверяемые требования к серверу

| ID | Требование | Признак готовности при реализации |
|---|---|---|
| R01 | Единый источник данных — сервер | После перезапуска сохраняются цеха, сотрудники, оборудование, фото и осмотры |
| R02 | Авторизация и доступ по цеху | Чужие ID не дают доступ к фото, оборудованию, истории и сообщениям |
| R03 | Приём снимка | JPEG/PNG проверяется по содержимому; действуют лимиты байтов и пикселей |
| R04 | Реальный анализ | Ответ модели проверен, версия сохранена; ошибка модели не даёт фиктивного успеха |
| R05 | Четыре технических статуса | Три цвета определённого состояния плюс UNKNOWN/GRAY для нехватки данных |
| R06 | Корректные координаты | Рамка соответствует снимку после нормализации поворота и попадает в его размеры |
| R07 | Независимость сообщения от сканирования | Осмотр сохраняется без пуша; «Сообщить» создаёт отдельное событие |
| R08 | Повторяемость запросов | Сетевые повторы с одним ключом не создают второй осмотр/сообщение |
| R09 | История и аудит | Видны исходная оценка, автор, серверное время и отдельное решение инженера |
| R10 | Адресные уведомления | Получатели ограничены цехом/ролью/назначением; открытая проблема не спамит |
| R11 | Паспорт конкретного оборудования | Данные берутся из БД по ID, а не генерируются моделью |
| R12 | Контролируемые ошибки | Сеть, таймаут модели и недостаточность изображения различаются |

Проверки R01–R12 относятся к будущей реализации; создание документа не означает их прохождение.

## Статусы и честность результата

| status | color | Значение |
|---|---|---|
| OK | GREEN | Поддерживаемых отклонений не обнаружено |
| WARNING | ORANGE | Возможная проблема |
| CRITICAL | RED | Предварительно серьёзный дефект; до проверки не подтверждённая поломка |
| UNKNOWN | GRAY | Недостаточно данных |

`review_status` хранится отдельно: `UNREVIEWED`, `CONFIRMED`, `REJECTED`. Подтверждённое состояние оборудования берётся из последней подтверждённой оценки. У красного результата модели нет автоматического права стать подтверждённым.

Обычная RGB-камера не измеряет температуру. Нельзя обещать диагностику любых агрегатов по модели для крепежа. Аудит подтверждает факт отправки сообщения, а не виновность сотрудника или физическую причину поломки.

## Приоритеты

- P0 сервера: R01–R08, паспорт, начальный каталог знаний и понятная документация.
- P1: расширенная история, проверки инженером и внутренние адресные уведомления.
- P2: FCM, двусторонняя офлайн-синхронизация, много узлов/дефектов и отчёты.

Базовая история записи осмотра и аудит отправки сообщения нужны сразу; расширенные экраны истории и процессы проверки могут добавляться позднее. Права доступа не откладываются до P1.

## Ограничения первой версии

Один осмотр — одно выбранное оборудование, один снимок, один проверяемый крепёж и одна итоговая оценка. Транспорт синхронный, если модель укладывается в согласованный таймаут. Переход на очередь и `202` требует обновления контракта.

БД — SQLite для демонстрации; фото — закрытые файлы. Телефон кеширует разрешённые данные, не подключается к серверной БД напрямую. API не предоставляет самостоятельной выдачи ролей или публичной регистрации.

Требуемую ТЗ AR-привязку реализует Константин. Сервер выдаёт двумерную область снимка, не трёхмерный якорь.

## Открытые решения команды

| Решение | Кто подтверждает | Рабочее предложение |
|---|---|---|
| Обязательные функции полного ТЗ и срок сдачи | Вся команда | Сверить с документами организаторов |
| Место крепления и демонстрационный агрегат | Константин + София | Один крепёж на макете, оборудование выбирается в приложении |
| Поддерживаемые моделью классы | София | Норма/недокручен/отсутствует/выкручен, только после проверки |
| Способ вызова, ресурсы и таймаут модели | София + Нияз | Адаптер к реальному Python/API-интерфейсу |
| Порог confidence | София + Нияз | Определить по контрольным изображениям; число не придумано заранее |
| Размеры снимка, поворот и схема JSON | Константин + Нияз + София | Контракты ниже |
| Инженерские права и рекомендации | Команда/заказчик | Матрица плана Нияза, только безопасные рекомендации |
| FCM | Константин + Нияз | После рабочего анализа и внутренних уведомлений |
