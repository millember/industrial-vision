# Шаг 10 — приёмка backend и сценарий демонстрации

## Что проверено локально

Проверка выполнена на PostgreSQL 17 и production-образе из текущих исходников. Отдельный Compose-стек не использовал рабочие контейнеры или данные сервера; HTTP-порт был привязан только к 127.0.0.1. TLS и физический Android этим запуском не проверялись.

| Проверка | Результат |
|---|---|
| Backend, включая права, повторы, инженерные решения и гонки | 84 теста прошли на PostgreSQL 17 |
| Синтетические демоданные и полный API-сценарий после перезапуска приложения | Включены в backend-тесты, повтор seed не дублирует записи |
| TypeScript и production-сборка frontend | npm run build прошёл |
| Go-команда запуска | go test -parallel 4 и go vet прошли |
| Production Docker image | Собран с uv.lock, запускается под UID 10001 и read-only filesystem |
| Реальный HTTP через Traefik v3.7.17 | Вход, закрытый Swagger, JS/CSS frontend, фото, сообщения, уведомления, проверка и закрытие прошли |
| Лимит шлюза | Фото больше 64 КиБ проходит; JSON больше 64 КиБ и тело загрузки больше 10 МиБ + 64 КиБ отклоняются |
| Две параллельные допустимые фотографии около 9 МиБ | Обе загрузки прошли с лимитами production-образа |

Новые HTTP-проверки находятся в `backend/tests/test_live_acceptance.py`. Они выключены по умолчанию и принимают только явно подготовленный одноразовый стенд на loopback. Временные пароли читаются из закрытого файла, а не передаются в аргументах; тесты не запускаются на production URL.

## Явные демоданные

Без модели обычная загрузка продолжает возвращать `MOCK/UNKNOWN`. Команда `seed-demo` создаёт отдельные синтетические примеры `OK/WARNING/CRITICAL` и четыре учётные записи:

| Логин | Роль | Цех |
|---|---|---|
| demo_worker | Рабочий | ДЕМО · Цех 1 |
| demo_master | Мастер | ДЕМО · Цех 1 |
| demo_engineer | Инженер | ДЕМО · Цех 1 |
| demo_foreign | Рабочий | ДЕМО · Цех 2 |

Создаются два макета `DEMO-IV-001/002`, паспорта, виды дефектов и четыре сохранённых синтетических осмотра. Все результаты имеют `analysis_source=MOCK`, `model_version=null` и объяснение, что распознавание не выполнялось. Демоснимок — одноцветное тестовое изображение, а не фотография распознанного дефекта.

На ноутбуке с отдельной БД разработки и заданным DATABASE_URL:

```bash
ANALYSIS_MODE=mock PHOTO_STORAGE=local uv run --directory backend python -m app.manage seed-demo
```

Пароль от 12 символов вводится дважды через getpass и используется только для демонстрационных сотрудников. Вывод содержит логины и ID без пароля. Повтор команды не создаёт копии и не меняет существующие пароли. При несовпадении роли, цеха, пароля или инвентарной записи команда останавливается, не перезаписывая чужие данные.

## Показ через Swagger

1. Войти в кабинет администратором, открыть `/industrial-vision/docs`. Убедиться, что операции разделены по русским разделам и имеют примеры.
2. Через `/auth/token` войти как demo_worker. Для Authorize использовать только значение токена без слова Bearer. Для проверки сотрудника с отдельными правами используйте отдельный браузерный контекст или HTTP-клиент без cookie администратора.
3. Открыть оборудование своего цеха, паспорт и сохранённые демоосмотры. Проверить, что demo_foreign получает 404 для этих же ID.
4. По демоосмотру WARNING или CRITICAL создать сообщение с новым UUID в Idempotency-Key. Повторить с тем же ключом — report_id и ответ не меняются.
5. Войти как demo_master или demo_engineer и получить внутренние уведомления. Отметить прочтение. Объяснить, что FCM-пуша нет.
6. Как demo_engineer подтвердить исходную оценку. Первый expected_review_id — null. Открыть исходный результат и цепочку решений; повтор с устаревшей версией должен получить 409.
7. После демонстрационного ремонта загрузить новый снимок оборудования. Ответ пока UNKNOWN, поскольку модели нет. Инженер вручную проверяет этот новый осмотр и отправляет CONFIRMED/OK.
8. Как demo_master получить проблему, взять latest_report_id и закрыть с reason, verification_review_id нового решения и expected_report_id. REPAIRED отличается от FALSE_ALARM; подтверждение дефекта не равно ремонту.
9. Перезапустить только контейнеры сервиса и БД, затем повторно прочитать фото, историю, решение и закрытие. Не удалять volumes.

После закрытия старый демоосмотр не создаёт новую проблему. Для повторного показа используйте ещё не закрытый пример либо отдельную БД демонстрации; не редактируйте историю в SQL.

## Рабочий сервер: граница готовности

Read-only SSH-проверка показала старый runtime-релиз `f1e36e6c7091f02e8a7527c76e7b62307a4f444a`. Docker на сервере требует интерактивный sudo. Локальная приёмка не означает, что новый релиз уже запущен в production.

Перед активацией подготовьте проверенный релиз и резервные копии БД, фото, текущего маршрута и указателей. Сохраните старые releases и volumes. Не запускайте старый pending, принимая его за новый релиз. Общая блокировка — `~/services/.home-server-deploy-lock`.

После подготовки актуального pending на сервере:

```bash
sudo ~/services/industrial-vision/start
```

Для демонстрации в закрытом `~/services/industrial-vision/private/database.env` явно задаются `ANALYSIS_MODE=mock` и `PHOTO_STORAGE=local`; без этого mock не включается автоматически. После запуска актуального релиза:

```bash
sudo ~/services/industrial-vision/start demo
```

Пароль выбирается в серверном терминале, не в чате. При обновлении также нужен проверенный маршрут `deploy/traefik.yaml`: новый отдельный upload-router разрешает 10 МиБ + 64 КиБ и ограничивает параллельность двумя запросами, остальные JSON-маршруты сохраняют 64 КиБ. Проверить маршрутизацию, frontend assets, закрытость Swagger, реальную загрузку фото и обычную проверку TLS после активации.

## Что остаётся открытым

- Активация и проверка нового релиза на рабочем сервере после интерактивного sudo.
- Проверка через актуальный Android APK на физическом телефоне и из внешней сети.
- Настоящая модель, контрольные фотографии и проверка качества распознавания (отложенный шаг 6).
- AR и FCM; восстановление из независимой резервной копии этим тестом не подтверждается.

Шаг 10 завершает локальную серверную приёмку текущего MOCK-сценария. Полный продукт нельзя считать принятым до закрытия перечисленных интеграционных ограничений.
